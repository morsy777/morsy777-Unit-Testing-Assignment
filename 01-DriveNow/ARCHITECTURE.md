# Architecture Tests

## 1. Failures on the Starter

| Rule | Failure | Why it matters for testing |
|---|---|---|
| `Application_ShouldDependOnlyOnDomain` | Failed because `DriveNow.Application` depends on `DriveNow.Infrastructure` as well as `DriveNow.Domain`. | Creates tight coupling between application logic and infrastructure, making unit testing harder. |
| Exception naming rule | Failed because exception classes did not follow the required naming convention: they must end with `Exception` and live in `DriveNow.Domain.Exceptions`. | Consistent naming and namespaces make exceptions easier to identify and maintain. |
| Test class naming | `TestClasses_ShouldEndWithTests` failed because `AutoGeneratedProgram` does not end with `Tests`. | The test included compiler-generated classes instead of checking only actual test classes. |
| `TestMethods_ShouldMatchNamingPattern` | Failed because the test included compiler-generated methods and inherited methods such as `get_Dates` and `GetType()`. | These methods are not developer-written test methods and should not be included in naming validation. |

## 2. Additional Issues & Fixes

### Issue 1: Application Layer Dependency

The Application Layer directly depended on Infrastructure, violating the intended dependency direction.

Removing the Infrastructure project reference allowed the tests to pass, but caused compilation errors because Application still needed repository implementations.

**Note:** Repository interfaces should be defined in Application (or Domain when appropriate), while their implementations belong in Infrastructure.

### Issue 2: Test Method Naming Convention

The naming test initially checked compiler-generated property accessors (e.g., `get_Dates`) and inherited methods (e.g., `GetType()`).

**Fix:**
- Used `BindingFlags.DeclaredOnly` to exclude inherited methods.
- Skipped compiler-generated methods using `CompilerGeneratedAttribute`.
- Skipped special methods using `IsSpecialName`.
- Fixed the loop to iterate over the filtered `methods` collection instead of calling `type.GetMethods()` again.

**Result:** The naming convention test passed successfully.

## 3. Naming Rules Test Design

Initially, the naming test data contained only the required suffix and namespace. However, different naming rules apply to different production assemblies.

To address this, I added a third parameter, `layer`, to `NamingRules` so each rule specifies the assembly it should inspect.

```csharp
public static TheoryData<string, string, string> NamingRules => new()
{
    { "Repository", "Repositories", Infrastructure },
    { "Service", "Services", Infrastructure },
    { "Exception", "Exceptions", Domain }
};
```

This allows the same parameterized test to apply each naming rule to the appropriate assembly instead of checking every rule against a single layer.
