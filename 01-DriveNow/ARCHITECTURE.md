# Architecture Tests

## Failures on the Starter

| Rule | Failure | Why it matters for testing |
|---|---|---|
| `Application_ShouldDependOnlyOnDomain` | Failed because `DriveNow.Application` depends on `DriveNow.Infrastructure` as well as `DriveNow.Domain`. | This creates tight coupling between the application logic and infrastructure implementation. It makes unit testing harder because application code may depend on infrastructure details instead of depending on abstractions. |
| Exception naming rule | Failed because exception classes did not follow the required naming convention: they must end with `Exception` and live in `DriveNow.Domain.Exceptions`. | Consistent naming and namespace conventions make exception types easier to identify and locate. This also helps keep domain exceptions organized in one place. |
| Test class naming | `TestClasses_ShouldEndWithTests` failed because `AutoGeneratedProgram` does not end with `Tests`. This is a compiler-generated class, not a test class written by the developer. | The architecture test initially checked every class in the test assembly, including compiler-generated classes. This caused a false failure because the naming rule is intended for test classes, not compiler-generated types. The test should be adjusted to check actual test classes only. |
| `TestMethods_ShouldMatchNamingPattern` | The test failed because the compiler-generated `AutoGeneratedProgram` type contains a method whose name does not match the required naming pattern. | The test checked all methods in the assembly, including compiler-generated methods that are not part of the actual test code. The test should exclude compiler-generated types or inspect only the relevant methods to avoid false failures. |

## Naming Rules Test Design

Initially, the naming test data contained only the required suffix and namespace. However, different naming rules apply to different production assemblies.

To address this, I added a third parameter, `layer`, to `NamingRules` so each rule specifies the assembly it should inspect.

```csharp
public static TheoryData<string, string, string> NamingRules => new()
{
    { "Repository", "Repositories", Infrastructure },
    { "Service", "Services", Infrastructure },
    { "Exception", "Exceptions", Domain }
};
```

This allows the same parameterized test to apply each naming rule to the appropriate assembly instead of checking every rule against a single layer.
